# Planning Document — 10 Rules (index)

Source: `github.com/cskwork/planning-doc-rules`. Turns an agent into a senior planner; derived from
Korean planning literature (*기획의 정석* 등) + NIPA RFP guidance. A planning doc is a decision document:
**Why → What problem → Who → What to build → How to execute → How to verify.**

Full content (all ten rules + the document skeleton) is in `ten-rules.md` — open it for any planning doc.

| # | Rule |
|---|------|
| 01 | Anchor "Why" first — never start with "what to build" |
| 02 | Define the problem as an As-Is / To-Be gap |
| 03 | Order sections by the reader's worries (need → alternatives → cost/value → feasibility → risk → execution → measurement) |
| 04 | Separate claim from evidence; mark assumptions |
| 05 | Derive requirements from user scenarios, not feature lists |
| 06 | Specify requirements without ambiguity (ID, inputs, outputs, acceptance criteria) |
| 07 | Connect IA → Flow → Wireframe → Spec, traceably |
| 08 | Define policy and exceptions first (where schedules actually slip) |
| 09 | Prove feasibility with numbers and a phased plan |
| 10 | Close the loop through QA, launch, operations, KPI |

Read `ten-rules.md` in full when drafting; spot-check against the relevant rules when reviewing.
