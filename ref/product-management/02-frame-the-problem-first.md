# Rule 02 — Frame the Problem Before the Solution

> 해결책을 말하기 전에 누구의 어떤 문제인지부터 못 박아라.
> Pin down whose problem and which problem before naming any solution.

## Why

Most failed products solve a problem no one has, or solve a real problem for the wrong person. Disciplined problem framing forces you to name the customer, the context, and the pain before debating features. The Lean Startup (Eric Ries) treats every product as a hypothesis about a customer problem; if the problem is wrong, no amount of execution saves you. A sharp problem statement is reusable across every later decision.

## How to apply

- Write the problem as: who, in what situation, struggles to do what, and why it matters.
- Separate the problem statement from any proposed solution; ban solution words in it.
- Quantify the problem's size and frequency with evidence, not assertion.
- Name the riskiest assumption inside the framing and plan to test it first.
- Get explicit agreement on the problem from stakeholders before scoping work.

## Checklist

- [ ] Problem statement names a specific customer and context
- [ ] No solution or feature language appears in the problem statement
- [ ] Problem size or frequency is backed by evidence
- [ ] The riskiest assumption is identified and testable
- [ ] Stakeholders have signed off on the problem, not just the plan
